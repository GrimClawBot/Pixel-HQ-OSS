# Pixel HQ Support

Pixel HQ is an Alpha project. Support is community/maintainer best-effort and no response-time SLA is promised.

## Bugs

Use the repository's **Bug report** issue template for reproducible public-safe defects.

Include:

- commit/tag tested;
- Node.js version and OS;
- minimal reproduction steps;
- expected vs actual behavior;
- sanitized logs only when useful.

Do not include credentials, private infrastructure coordinates, personal data, private evidence, or exploit payloads.

## Feature requests

Use the **Feature request** template. Explain the problem first, then the proposed behavior. Roadmap ideas are welcome, but a discussion or issue does not itself authorize implementation.

## Security issues

Do **not** file a normal public issue containing exploit details. Follow [`SECURITY.md`](SECURITY.md).

If GitHub private vulnerability reporting is available for the repository, use the **Security** tab. If it is unavailable, open only a minimal non-sensitive issue asking the maintainer for a private reporting channel; do not include the vulnerability details in that issue.

## Questions

Until GitHub Discussions is enabled, use an issue only for questions that are specific, reproducible, and useful to future contributors. General project planning should stay out of bug reports.

## What maintainers can reasonably help with during Alpha

- local simulator setup;
- contract/test behavior;
- documented architecture boundaries;
- contribution workflow;
- public-safe reproduction of failures.

Maintainers cannot provide support for private deployments, undisclosed infrastructure, production authentication, secret management, or unsupported production exposure based on this Alpha source.
